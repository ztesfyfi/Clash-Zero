## Open-Box 操作体验与功能对齐（已确认，按功能完整实现）

本项目以 Open-Box 公开文档、公开界面和公开操作说明作为交互与功能参考，目标是尽可能复现其“订阅管理 → 出站节点 → 代理策略 → 目标分流”的操作体验，并在 Clash-Zero 中实现可实际运行的对应功能。此要求不是只做 UI 示意或需求记录。

### 对齐范围

1. **订阅管理**
   - 订阅导入、协议解析、独立重命名、更新、启停、删除、分享/导入来源管理。
   - 订阅折叠/展开、节点清单、节点类型、延迟颜色与测速状态。
   - 节点重命名、搜索、筛选、详情；节点身份使用稳定 ID，订阅更新后尽可能保持用户自定义名称和组成员关系。
2. **出站节点**
   - 静态组与动态组可以混合使用；静态组从指定订阅中逐个选择节点。
   - 动态组按一个或多个关联关键字自动收编节点；关键字支持 OR/AND，留空行为需有明确、可见的“全部节点”语义。
   - 可叠加订阅范围、地区、节点类型等筛选；地区只能使用已验证的出口 IP 归属信息。
   - 组内显示实际节点名称、所属订阅、类型、延迟和匹配原因；支持预览、排序、启停、编辑和删除。
3. **代理策略**
   - 支持手动选择、自动择优、故障转移、负载均衡等模式。
   - 策略成员可引用出站节点组和其他代理策略；支持自由组合、排序、嵌套和健康状态查看。
   - 对循环引用、空成员、禁用成员、失效引用和不兼容成员提供保存前校验及明确错误。
   - 多组引用同一节点时共享探测结果，避免重复测速；失败与恢复按确认次数处理。
4. **目标分流**
   - 支持域名、后缀、关键词、IP/CIDR、GeoIP、GeoSite、本地规则集和远程规则集。
   - 支持站点/策略集合、优先级、规则顺序、AND/OR/NOT、默认出口和规则集导入预览。
   - 提供规则命中预览；能在运行环境允许时验证真实请求的最终出口、DNS 与命中规则。
5. **运行与诊断**
   - 图形界面修改后生成 Mihomo 配置并进行结构与引用校验。
   - 对配置进行安全写入、差异检查、加载结果确认和失败回滚；不能只更新数据库而不应用到内核。
   - 显示实际运行的策略、当前节点、健康状态、错误日志和规则命中信息。

### 交互复现要求

- 优先复现 Open-Box 的页面层级、操作顺序、控件语义、列表展开/收起、编辑对话框、关键字输入、即时预览、成员排序和状态反馈。
- Clash-Zero 采用 Android 原生适配：纵向列表、适合触屏的控件、清晰的返回/保存/取消操作；不照搬桌面端密集布局。
- 订阅管理、出站节点、代理策略、目标分流仍作为独立一级页面；保留用户已确认的首页结构和纵向列表偏好。
- 所有显示状态必须来自真实数据；不允许用假节点、假测速、假健康状态或仅存在于 UI 的开关。

### Mihomo 适配与边界

- Open-Box 的内核是 sing-box，Clash-Zero 的内核是 Mihomo。只移植可观察的产品行为和功能语义，配置编译、代理组类型、规则语法、规则提供器、DNS 与运行状态必须按 Mihomo 实际支持的能力实现。
- Open-Box 仓库声明其自有程序为闭源专有软件。因此本项目不复制其专有源代码、资源或受限实现；以公开文档、公开截图和公开操作行为为依据独立实现。第三方组件仅按各自许可证处理。
- 如 Mihomo 与 Open-Box 的语义存在差异，界面应明确说明并采用 Mihomo 可验证的等效行为，不得伪称完全相同。

### 完成与验收标准

每个模块必须同时满足：界面操作完整、数据持久化正确、配置生成正确、Mihomo 能加载、运行结果可验证、订阅更新/重启/失败场景有测试。仅完成界面、仅提交文档或仅通过 Kotlin 编译均不算模块完成。

按以下顺序实施：订阅与节点数据层 → 订阅管理交互 → 出站节点组 → 代理策略 → 目标分流与规则集 → 配置事务与运行诊断 → 全链路回归测试。每一阶段提交代码并检查 CI，明确标注尚未完成的能力。

# Clash-Zero 产品需求与实现说明

> 更新时间：2026-11-13。本文使用简体中文，区分已确认需求、当前代码实现和仍待完成事项。未标记为“已实现”的能力不得视为已经交付。

## 一、产品目标

以 Mihomo 为 Android 代理内核，通过图形界面管理订阅节点、出站节点组、代理策略和目标分流。所有已保存配置最终必须进入 Mihomo 实际配置加载链路，且必须通过内核配置校验；不能只保存在 Room 数据库中。

## 二、一级菜单

主界面只保留以下一级入口：

1. 启动 / 停止
2. 订阅管理
3. 出站节点
4. 代理策略
5. 目标分流
6. 设置

节点组直接在“出站节点”页面管理；策略组直接在“代理策略”页面管理。不再增加“全部节点 / 节点组”或“策略组”等二级菜单。

## 三、功能需求

### 3.1 订阅管理

- 添加、编辑、删除、更新订阅，支持手动更新和定时更新。
- 订阅链接粘贴/导入页面必须提供独立的订阅重命名选项；订阅名称与 URL 分开保存，后续可编辑名称。
- 订阅列表采用三级展开交互，每个订阅独立展开，不跳转到其他页面：
  1. **收起状态**：显示订阅名称和必要的基本信息。
  2. **概览状态**：点击订阅一次后展开节点统计，显示节点总数，以及绿色（低延迟）、黄色（中等延迟）、红色（高延迟）、灰色（超时/无有效测速结果）四类数量。
  3. **节点详情状态**：再次点击同一订阅后，展示该订阅的全部节点，列表布局参考 Clash 代理列表，显示用户重命名后的节点名称、节点类型（如 VLESS、VMess）、延迟和状态。
  4. **再次点击**：折叠该订阅，回到收起状态。再次点击循环进入概览、节点详情。
- 概览统计必须由该订阅的节点测速数据实时/缓存汇总得出，不得用订阅总量或其他订阅的节点数据代替。
- 延迟颜色阈值必须统一配置并在界面中有明确含义；超时、尚未测速或测速失败显示灰色，不能误显示为红色高延迟。
- 展示所有订阅导入的具体节点及来源订阅。
- 提供节点详情、测速、重命名、搜索和筛选。
- 可从订阅节点选择成员并加入出站节点组。
- 节点成员关系必须使用稳定节点标识，不能只依赖可变显示名称；节点重命名后，静态组成员关系必须保持有效。

### 3.2 出站节点

本页只管理节点组；具体节点仍在“订阅管理”中管理。节点组列表及编辑界面必须能看到实际节点名称，不能只显示节点数量。

- 静态节点组：
  - 新建/编辑时先选择一个或多个订阅。
  - 选择订阅后，展开该订阅的具体节点清单，再从清单中勾选节点加入节点组。
  - 节点清单显示节点名称、节点类型和延迟状态；显示用户重命名后的节点名称。
  - 支持跨多个订阅选择、批量勾选、取消选择和移除成员。
  - 保存后在节点组详情中显示实际成员节点名称；重新打开编辑时恢复已选状态。
  - 成员关系使用订阅 UUID + 稳定节点 ID，不得使用可变显示名称作为唯一关联。
- 动态节点组：
  - 编辑界面提供明确的“关联关键字”输入框，用户填写用于匹配节点名称的关键字。
  - 按关键字自动匹配订阅节点，并显示实时/预览匹配结果。
  - 匹配结果显示节点名称、所属订阅、节点类型和延迟状态。
  - 关键字修改后可先预览，再保存；订阅更新或节点重命名后重新计算匹配结果。
  - 关键字匹配必须大小写不敏感，并明确多个关键字的匹配逻辑；不得把关键字误作订阅名称前缀或地区代码。
  - 保留地区筛选作为可选附加条件；地区必须来自节点实际出口 IP 的验证结果，不能仅根据节点名称推断。
- 支持创建、编辑、删除、启用和停用。
- 删除仍被代理策略引用的节点组时，必须提示引用关系并防止误删。

### 3.3 代理策略

本页统一管理策略组。

- 类型：手动选择、自动择优、故障转移、负载均衡。
- 成员可以引用出站节点组或其他代理策略。
- 支持成员添加、移除、排序和嵌套组合。
- 支持设置测速 URL、测速间隔、超时和负载均衡参数。
- 展示当前成员、延迟和健康状态。
- 检查循环引用、无效引用、重复成员和不支持的组合。
- 嵌套深度最多 5 层。
- 不直接绑定单个订阅节点；具体节点归订阅管理，节点组织归出站节点。

### 3.4 目标分流

负责识别访问目标并决定出口，不直接绑定具体节点。

- 匹配类型：完整域名、域名后缀、域名关键词、IP、IP/CIDR、GeoIP、GeoSite、规则集。
- 远程规则集与本地规则集可以共存。
- 支持规则优先级、启用/停用、编辑、删除和分组。
- 出口可以是代理策略、DIRECT 或 REJECT。
- 支持默认出口和绕过大陆规则模板。
- 提供规则预览；规则预览与真实连接诊断必须分开。
- 必须遵循 Mihomo 自身的 DNS、嗅探和规则匹配语义，不得直接照搬其他内核的域名/IP 判定行为。

### 3.5 设置

- Mihomo 内核、DNS、TUN、IPv6。
- 自动测速、故障检查、超时、并发和测速 URL。
- GeoIP、GeoSite、规则集更新。
- 配置备份、导入、导出。
- 日志、诊断、外观和语言。

## 四、明确排除的功能

- 不实现 Android 应用 / 包名分流。
- 不允许按已安装 APP 选择出口。
- 不允许目标规则直接绑定单个代理节点，应通过代理策略引用出站节点组。
- 不重复实现 Mihomo 已有的 URL-Test、Fallback 和 Load Balance 内核能力；APP 负责图形化配置、组合、校验和状态展示。

## 五、性能保护参数（已确认）

| 参数 | 确认值 |
|---|---:|
| 自动择优测速间隔 | 300 秒（5 分钟） |
| 故障转移检查间隔 | 60 秒（1 分钟） |
| 连续失败确认次数 | 2 次 |
| 恢复成功确认次数 | 2 次 |
| 单次测速超时 | 5000 毫秒 |
| 最大测速并发数 | 5 |
| 手动测速 | 立即执行 |

### 5.1 测速调度与缓存要求

- 同一节点被多个策略引用时，共享测速结果。
- 同一轮调度中，同一节点和同一测试 URL 只探测一次；相同请求并发时去重。
- 缓存键至少包含稳定节点标识和测速 URL，并记录延迟、结果、成功状态和时间戳。
- 最大并发数为 5，单次探测超时为 5000 毫秒。
- 连续失败 2 次才标记故障；恢复连续成功 2 次才重新标记健康。
- 手动测速立即执行，但仍受并发限制和请求去重约束。
- 故障检查不能退化为无间隔全量测速。

### 5.2 配置生成和应用

- 节点组、代理策略和目标分流统一编译为 Mihomo 配置。
- 保存配置前检查循环引用、无效引用、规则冲突、重复规则和无效目标。
- 生成后必须经过 Mihomo 原生配置解析和校验；失败时不得应用。
- 配置未变化时复用结果；仅修改相关配置时才重新生成。
- Mihomo 支持热更新时优先增量更新；只有必要时才重载内核。
- 规则预览和真实路由诊断必须分别实现。

## 六、数据关系

`订阅管理（具体节点） → 出站节点（节点组） → 代理策略（策略组） → 目标分流（目标到出口映射） → Mihomo`

所有关联使用稳定 ID；显示名称只用于界面展示。

## 七、旧 APP 分流数据迁移

数据库从版本 6 升级到版本 7 时：

1. 删除 matcherType 为 `PROCESS_PACKAGE` 的旧匹配条件。
2. 同一条规则若仍有域名/IP 等其他条件，则保留该规则和其他条件。
3. 如果规则只包含 APP 条件，删除该条件后自动停用规则，避免空条件规则意外匹配全部流量。
4. 不删除节点组、代理策略、订阅、其他分流条件或其他用户数据。
5. 新建和编辑规则时，校验器拒绝 `PROCESS_PACKAGE` 类型。

该迁移会在应用升级并打开 Room 数据库时执行。仅检查代码无法读取用户手机上的实际数据库，因此不能提前报告用户设备中具体有多少条旧记录。

## 八、当前代码实现状态

### 已接入代码

- 数据库升级至版本 7，并增加旧 APP 分流条件清理迁移。
- 规则校验器不再接受 APP 包名匹配条件。
- 代理策略编辑界面移除 APP 选择和 APP 分流写入逻辑。
- 配置加载前生成独立的 `strategy.json` 覆盖文件，不直接改写订阅原始 `config.yaml`。
- Mihomo 原生配置处理流程读取该覆盖文件，将生成的代理组追加到原始配置，并把图形化规则放在基础规则之前。
- 当前生成器已覆盖静态出站节点组、基础策略组类型，以及 DOMAIN、DOMAIN-SUFFIX、DOMAIN-KEYWORD、IP-CIDR、GEOIP、GEOSITE 和基础 AND/OR 规则。
- 策略编辑后发送配置变更广播，触发当前配置重新生成和加载。

### 出站节点界面补充要求（已确认，待开发）

- 当前静态组编辑表单只有组名、关联名称和地区字段，没有订阅选择器，也没有订阅内节点多选列表；当前无法从 UI 完成静态组成员配置。
- 当前动态组的 nameTag 逻辑用于匹配带订阅前缀的名称，不等同于用户输入的任意“关联关键字”。需要调整为独立的关键字匹配字段和匹配器，并保留原有订阅关联名称/地区能力时避免语义混淆。
- 当前组列表只展示组名称、类型和关联字段，未展示组内实际节点名称；必须补充成员预览/详情。
- 静态组成员数据模型已保存 profileUuid、proxyKey、proxyName，但需要确认 proxyKey 在所有订阅解析路径中稳定生成，并实现按订阅列出节点及节点选择的完整 UI。
- 现有配置编译器只针对当前 profileUuid 过滤静态组成员；需要在编译时确认目标订阅配置上下文与成员所属订阅一致，不能把其他订阅的节点名直接写入当前配置。

### 订阅管理界面补充要求（已确认，待开发）

- 当前 ProfilesActivity / ProfilesDesign 仍是原有订阅卡片和菜单交互；NewProfileActivity 当前创建订阅时默认使用“新配置”名称，URL 导入流程没有在粘贴页提供独立重命名字段。
- 当前订阅列表尚未实现“收起 → 概览 → 节点详情 → 收起”的三级循环展开。
- 当前 Proxy 数据模型虽包含名称、类型和 delay，但不能据此推断已经能按订阅可靠列出全部节点；必须建立订阅 UUID 与节点稳定 ID 的关联，并为非当前活动订阅提供安全的节点枚举方式。
- 节点延迟颜色阈值需统一定义，避免 UI 与统计口径不一致；“未测速”和“超时”均归灰色。
- 订阅列表的概览统计与节点详情必须严格限定在当前订阅，不得混入其他订阅或 Mihomo 内置策略组。

### 尚未完成，不能视为已交付

- 动态节点组的完整节点枚举、订阅/地区/节点类型条件匹配和动态预览。
- 节点地区识别结果缓存，以及按出口 IP 验证地区。
- 规则集提供器完整生成、远程下载、更新和本地文件规则集。
- 完整 AND/OR/NOT 条件组语义及规则冲突检测。
- 统一测速调度器、跨策略测速缓存、并发上限 5、失败/恢复双重确认状态机。当前生成器仅把 300 秒、60 秒、5000 毫秒和 max-failed-times=2 写入 Mihomo 策略组；Mihomo 的 max-failed-times 不是“连续失败 2 次且恢复连续成功 2 次”的完整状态机，不能当作已经实现。
- 设置页面中的测速参数编辑。
- 规则预览和真实路由诊断界面。
- 完整配置差异缓存、增量热更新及回滚机制。
- 真实设备端到端流量验证。

### 当前生成器的安全边界

- 当前生成器支持静态节点组，以及按订阅名称前缀筛选的基础动态节点组；动态筛选使用 Mihomo 的 `include-all` 和 `filter`。
- 空节点组、空策略组和没有有效目标的默认预设不会生成无效引用。
- 按出口 IP 归属地动态分组、复杂动态条件组合和规则集提供器仍未完整接入，不能宣称已经交付。
- 配置必须经过 Mihomo 原生加载校验；构建成功不等于运行时配置和真实流量已经验证。

## 九、验收标准

1. 一级菜单符合第二节，不出现节点组或策略组二级菜单。
2. 新规则不能使用 Android APP 包名匹配。
3. 旧数据库升级后不再保留 `PROCESS_PACKAGE` 条件；只剩 APP 条件的规则处于停用状态。
4. 静态节点组、代理策略和基础目标分流可以生成 Mihomo 配置并通过原生校验。
5. 动态组、规则集、复杂条件、测速缓存及调度器完成后，分别补充自动化测试。
6. 同一节点被多个策略引用时，一轮测速仅执行一次。
7. 测速并发不超过 5，超时为 5000 毫秒。
8. 连续失败和连续恢复均按 2 次确认。
9. 策略存在循环引用或目标引用无效时，禁止保存或应用。
10. 节点重命名后静态组成员关系仍有效。
11. 规则预览不能冒充真实路由诊断；真实路由必须通过实际请求验证。
